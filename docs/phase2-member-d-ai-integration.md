# 第二阶段任务文档：成员 D

## 任务主题

个性化多信息分析引擎与四方联调：把视频识别、用户需求、商品事实和证据组合成可解释的结构化结论。

## 本阶段目标

将当前“证据置信度 + 条件数量 + 视觉置信度”的固定加权模型升级为逐项需求匹配。AI 可以参与需求解析和解释生成，但所有结论必须建立在已提供的商品事实和证据之上。

## 允许修改范围

- `backend/app/services/vision/`
- `backend/app/services/verification/`
- `backend/app/prompts/`
- `backend/app/category_profiles/`
- AI 配置、启动部署和集成测试

共享 API、类型、路由和根配置的修改必须先与项目负责人确认，并同步更新 `docs/04-api-contract.md`、前端类型和后端 Pydantic 模型。

## 具体任务

1. 定义增量合同：需求分析项、匹配状态、商品事实、决策链路和未知项；保留现有接口兼容性。
2. 将用户结构化条件和原始文本归一化为带优先级的需求集合，不能只统计字段数量。
3. 调用 C 的检索服务获取与每条需求相关的商品事实和证据。
4. 实现“需求 → 商品事实 → 证据 → 结论”的分析流程，输出满足、冲突、未知三种状态。
5. 设计证据约束的模型提示词和结构化输出校验；模型不得自行补充不存在的商品事实或来源。
6. 推荐分数使用需求权重和匹配状态计算，并把每个维度的理由返回给前端。
7. 实现再推荐逻辑：继承原需求，合并用户反馈和条件修改，过滤已看过商品，并解释本轮变化。
8. 保留 Mock 和规则降级；外部模型必须从环境变量读取配置，设置超时、异常处理和不可用提示。
9. 负责四方联调，验证 A 的动态候选、B 的完整条件、C 的证据检索和结果接口能够贯通。

## 验收标准

- 同一商品在不同用户画像下会产生不同的逐项匹配结果和推荐依据。
- 商品从“满足”变为“冲突”时，必须有对应商品事实或证据支撑。
- 证据不足时输出“未知/待确认”，不生成无来源结论。
- 用户反馈进入再推荐请求，并实际影响下一轮候选或匹配结果。
- AI 服务不可用时能降级，且不会伪装成完整 AI 分析。
- 后端测试、集成测试和前端构建全部通过。

## 联调顺序

先与 A 确认候选商品和数据覆盖，再与 C 确认检索返回结构，随后给 B 提供稳定结果样例，最后完成完整视频到推荐到再推荐的演示链路。
