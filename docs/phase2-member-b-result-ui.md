# 第二阶段任务文档：成员 B

## 任务主题

个性化需求输入与结果解释 UI：让用户能看到系统如何根据自己的需求判断商品，而不是只看到固定摘要和总分。

## 本阶段目标

动态表单、自由文本和语音转写结果都要完整进入验证请求；结果页按照接口返回的需求分析展示“满足、冲突、未知”和对应证据，并支持带原因的再推荐。

## 允许修改范围

- `frontend/src/features/conditions/`
- `frontend/src/features/verification/`
- `frontend/src/features/comparison/`
- `frontend/src/components/dynamic-form/`
- `frontend/src/components/evidence/`

不得直接修改 Mock 数据、后端逻辑、共享路由、Pinia 或 API 合同。若需要新增字段，先提交给 D 和项目负责人确认。

## 具体任务

1. 从 category profile 动态生成完整条件表单，提交所有已填写的字段和原始文本。
2. 明确区分结构化条件、文本需求和语音转写内容，不再用固定鼠标字段或固定选项。
3. 将结果页的固定推荐文案、固定百分比和固定结论替换为接口返回值。
4. 新增逐条需求分析卡片：显示需求、优先级、商品事实、匹配状态、解释和 `source_ids`。
5. 将支持、风险、未知结论与证据详情联动；没有来源的结论不得展示为事实。
6. 完成“不满意”反馈：提供原因选择、补充说明和条件修改，并按合同调用 `/api/recommendations/rerun`。
7. 处理加载、接口错误、证据为空、AI 降级和结果为空等状态。

## 验收标准

- 修改预算、用途或偏好后，结果页的需求匹配状态和推荐依据会随之变化。
- 页面不再显示与接口结果无关的固定摘要或固定购买渠道数量。
- 每条支持、风险和未知结论都能定位到至少一个来源。
- 点击再推荐并填写原因后，请求中包含原因和继承后的需求。
- `npm run build` 和 TypeScript 检查通过。

## 注意事项

页面只负责展示后端分析结果，不在前端重新计算推荐分数。数据不足时应显示“未知/待确认”，不能用乐观文案替代后端结论。
