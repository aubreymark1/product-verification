# 第二阶段任务文档：成员 A

## 任务主题

视频识别链路与演示数据建设：让演示流程使用动态输入和可对比的数据，而不是固定商品、固定候选和固定结果。

## 本阶段目标

用户在视频中圈选对象后，前端通过接口获得候选商品；用户选择的商品、类目和视频上下文进入后续验证流程。Mock 数据继续作为演示资料库，但必须能支撑不同用户需求得到不同推荐结果。

## 允许修改范围

- `frontend/src/features/video/`
- `frontend/src/features/object-selection/`
- `frontend/src/features/product-confirmation/`
- `data/mock/`
- 与视频和演示数据直接相关的文档

不得直接修改共享路由、Pinia、API 合同、B 成员结果页或 C/D 成员后端目录。

## 具体任务

1. 将视频页中的固定 `video_id`、固定候选商品、固定置信度和固定商品名称替换为接口返回值。
2. 接通 `GET /api/videos/{video_id}` 和 `POST /api/vision/identify`，保留识别失败时的可理解错误状态。
3. 用户切换候选商品后，后续验证请求、商品展示和购买渠道必须使用当前选中商品。
4. 与 D 确认类目字段后，补充至少 4–6 个定位不同的同类商品，形成预算、用途、连接方式、重量或续航等方面的真实取舍。
5. 为每个演示商品补齐通用商品事实和支持/风险/待确认证据；来源必须有稳定 ID，并明确 `demo_mock` 或真实来源类型。
6. 准备至少 6 组差异明显的用户画像，供联调验证推荐是否随需求变化。

## 验收标准

- 视频页不再依赖固定候选商品完成主流程。
- 选择不同商品后，提交的 `product_id` 始终正确。
- 至少两组用户需求能够得到不同的候选排序或需求匹配结果。
- 每个商品至少有一条支持证据、一条风险或限制证据；资料不足时允许明确为未知。
- `npm run build` 通过，并提交演示数据清单和未覆盖字段。

## 注意事项

Mock 数据由 A 维护，但字段结构必须先与 D 确认。不得伪造价格、评论、测评或来源；不得为了让某个商品胜出而修改公共推荐逻辑。
